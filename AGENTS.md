# AGENTS.md — `HiveMind-core`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

HiveMind-core is the hub: it listens for satellite connections, runs the
admission/policy chain that decides what each client is allowed to do, routes
messages between satellites and the agent backend (OVOS or another plugin),
and owns the client-credential database. Part of the
[HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol for
connecting satellite devices to a hub running
[OpenVoiceOS](https://github.com/OpenVoiceOS). Transport, agent, database, and
binary-payload behavior are pluggable via `hivemind-plugin-manager`; the wire
protocol itself lives in `hivemind_bus_client` and the community docs
(https://jarbashivemind.github.io/HiveMind-community-docs/04_protocol/).
Related repos: `hivemind_bus_client` (client library and Noise/crypto
primitives), `hivemind-plugin-manager` (policy/database/protocol plugin
contracts), `hivescope` (the e2e test harness used below).

## Layout / build / test

- Package module: `hivemind_core/`. Key modules: `protocol.py` (listener
  protocol, admission chain, encoding/crypto), `service.py` (process
  bootstrap, upstream connection), `database.py` (`ClientDatabase`, thin
  wrapper over a pluggable `DatabaseFactory` backend), `policy.py`
  (`PolicyChain`, `Verdict`, deny-code constants), `scripts.py` (the
  `hivemind-core` CLI — add/rename/blacklist clients and message types).
  Tests live in `tests/` (unit) and `tests/e2e/` (real-hub tests via
  hivescope) — do not create a second test directory.
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[test,integration]" --prerelease=allow`
- Run the suite in the foreground: `python3 -m pytest tests -q`. `tests/e2e/`
  boots a real hub through hivescope fixtures and needs the `test`/`integration`
  extras installed; `conftest.py` loads hivescope's pytest plugin only when
  hivescope is importable, so a plain unit run without those extras still
  passes without the e2e fixtures.
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is a
  bug to FIX at the source, not to work around with a pin downgrade.

## Working agreement (org-wide law)

- **Git identity is always** `JarbasAi <jarbasai@mailfence.com>`. Never set a
  per-repo override.
- **Never push `dev` or `master`.** Work on a feature branch and open a
  **draft** PR into `dev`. A human merges. You do not merge your own PRs.
- **Never merge or modify `Release X → master` PRs.** They are the maintainer's
  stable-release mechanism, generated by automation.
- **One commit per PR** (squash before pushing). Conventional commits; `feat:`
  only for a user-visible new capability. `fix:`, `docs:`, `chore:`, `ci:`
  otherwise.
- **Disclose AI authorship.** Every PR/issue/comment an agent writes carries, at
  the top: `> 🤖 Auto-generated by <model> via Claude Code — NOT human-reviewed.
  Verify before acting.` PR bodies are plain human prose (3–6 short paragraphs),
  no tables or section-symbol spray.
- **Never edit someone else's** issue, PR description, or comment. Add a comment
  instead; on your own PRs, edit the body rather than piling on comments.
- Keep durable text (README, docs, PR bodies, comments) timeless and standalone:
  no dates, no "currently/now/new", no meta-commentary about the edit itself.
- No scratch files, committed virtualenvs, `__pycache__`, `.pyc`, `.egg-info`,
  or build artifacts in a PR. `git show --stat` shows only intended files.

## Dependencies

- **Floor pins only** (`>=X.Y.Za1`), bumped when a feature or fix is actually
  needed — with a one-line comment saying why. No upper caps unless a specific
  released version is genuinely broken (say which and why). `pyproject.toml`
  already documents several such floor bumps inline (Noise PSK derivation,
  flood-cache dedup, identity rotation) — follow that pattern for new ones.
- **No lockfiles, ever.** Target the latest alphas (`--prerelease=allow`).
- Everything in `pyproject.toml` (deps, metadata, version). Never install from
  git — depend on a published PyPI alpha.
- This repo is **Apache-2.0**, not AGPL. Do not add GPL/AGPL dependencies.

## Tests

- Adversarial by default. A regression test must **fail before the fix and pass
  after** — prove it by reverting only the source (`git apply -R`, never
  `git stash` across worktrees) and watching the test flip.
- Tests must be mutation-proof: gutting the feature must fail the test. A test
  that only asserts a mock was called, without asserting the real behaviour, is
  weak — note it.
- Never skip a test because an optional dependency is missing.
- CI green is permission to review, not to merge. A non-trivial change gets an
  adversarial review before it lands.

## Repo-specific rules

- This is the hub, not a client: it owns the listener, the admission chain,
  and routing. A bug here (a wrong `Verdict`, a routing loop, a mis-parsed
  wrapper) affects every connected satellite, not one connection.
- **Wire back-compat is load-bearing.** This process speaks the HiveMind
  protocol to clients running older and newer library versions
  simultaneously. Never change the wire shape of an existing `HiveMessageType`
  and never add a new bus message type — extend an existing message or add a
  new `HiveMessageType` frame instead, and keep decoding tolerant of fields a
  legacy client omits.
- **Admission is on the hot path and must fail SAFE.** `PolicyChain` /
  `PolicyPlugin` verdicts gate every inbound frame; when a policy can't decide
  (backend unreachable, malformed wrapper, unknown message type) the correct
  outcome is deny/degrade with one of the existing deny codes
  (`BACKEND_UNAVAILABLE`, `MALFORMED_PAYLOAD` in `policy.py`), never
  fail-open. Do not add a code path that forwards a message when a policy
  decision is missing or ambiguous.
- **`Release X → master` PRs** are the maintainer's stable-release mechanism —
  never merge or modify them, per the org-wide rule above; it applies with
  extra force here since a stable HiveMind-core release is what most deployed
  hubs and their satellites pin against.
- **e2e tests boot a real hub.** `tests/e2e/` uses hivescope fixtures to spin
  up an actual `HiveMindListenerProtocol` and drive it over the wire (auth,
  broadcast, propagate, mesh routing, protocol-v3 matrix); they are the
  ground truth for protocol behavior, not the unit tests that mock the
  connection. When a change touches `protocol.py`, `policy.py`, or
  `database.py`, run the e2e suite, not just unit tests, before claiming it
  works.
- `ClientDatabase` is a thin wrapper over a pluggable `DatabaseFactory`
  backend (JSON, SQLite, or a `hivemind-plugin-manager` entry point) — do not
  hardcode assumptions about the backing store; go through the `ClientDatabase`
  / `Client` interface.
